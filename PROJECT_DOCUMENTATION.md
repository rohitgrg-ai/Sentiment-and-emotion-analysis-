# Emotion & Sentiment Analysis (NLP) — Project Documentation for Viva

## 1. One-minute summary
We build a system that reads a short social-media-style text and predicts:
- **Emotion** (6 classes): sadness, joy, love, anger, fear, surprise
- **Sentiment** (3 classes): negative, neutral, positive

Pipeline: raw data -> exploration (EDA) -> cleaning & balancing -> text cleaning -> train/test split -> TF-IDF features -> baseline classifiers -> evaluation and error analysis -> Streamlit demo app.

Key results (test set, 11,796 rows): Linear SVM macro-F1 = **0.963 (emotion)** and **0.946 (sentiment)**; a majority-class guess scores 0.048 and 0.167.

Two honest findings you should be ready to state:
1. The original data contained **label leakage** (emoji suffixes that encoded the labels). We detected and removed it.
2. The **sentiment labels were produced by a lexicon heuristic**, not by humans, so the sentiment score shows we can reproduce that heuristic, not that we understand true sentiment.

**Update, 9 Nov 2026:** the SVM's 0.963 only holds on data like its training set. On human-labelled GoEmotions text its accuracy is 0.303. The app now predicts emotion (7 classes including neutral) and sarcasm with a Twitter-based transformer, which scores 0.688 macro-F1 on that natural test. Sentiment still comes from the SVM. See section 7A.

## 3. Step-by-step: what was done and why

### Step 1 — Exploratory Data Analysis (EDA)
Looked at shape, columns, missing values, duplicates, class distributions and text lengths, with matplotlib/seaborn plots. Purpose: understand the data before touching it; this is where problems (duplicates, imbalance, odd emoji suffixes) were noticed.

### Step 2 — Data cleaning and balancing (`balance_dataset.py`)
Starting point: 416,809 rows. Actions, in order:

1. **Remove synthetic emoji suffixes (44,650 rows).** Some texts had emojis appended at the end (e.g. a sad face + a negative face) that directly encode the emotion and sentiment label. A model could read the emoji instead of the language -> *target leakage*. We stripped them with a regex.
2. **Drop contradictory texts.** If the *same text* appeared with different labels, it is ambiguous. 22,295 text groups (44,650 rows) were removed.
3. **Remove exact duplicates** (632 rows) so the same sentence cannot appear in both train and test.
4. Result: **371,527** clean unique texts.
5. **Balance both targets at once** by undersampling. Emotion classes had different sizes; the smallest had 9,830 rows, so every emotion gets 9,830 (total 58,980) and every sentiment gets 19,660. Hitting both targets exactly is a small flow problem; we solved it with an integer **max-flow (Dinic's algorithm)** that decides how many rows to take from each (emotion x sentiment) cell. All sampling uses seed 42, and the script asserts the balance before saving.

Why balance? With imbalanced classes, accuracy is misleading (a model that always predicts the biggest class looks good). Balanced data makes accuracy and macro-F1 meaningful.
Trade-off: undersampling throws away data (416k -> 59k) and some (emotion, sentiment) combinations become impossible, e.g. no "sadness + neutral" rows were selected.

### Step 3 — Text preprocessing (`preprocessing.py`)
`clean_text`: lowercase -> convert any emojis to words (optional `emoji` library) -> remove URLs -> collapse whitespace. We kept it light because TF-IDF with n-grams handles most variation, and heavy cleaning (stemming, stopword removal) can delete useful words like "not".

### Step 4 — Train/test split
80% train (47,184) / 20% test (11,796), `random_state=42`, **stratified on emotion x sentiment together** so both targets stay balanced in both splits. The test set is never used for fitting anything.

### Step 5 — Feature extraction: TF-IDF
Turns text into numbers. TF-IDF = term frequency x inverse document frequency: words frequent in a document but rare overall get high weight.
Settings: `max_features=50,000`, `ngram_range=(1,2)` (single words and word pairs, so "not happy" is captured), `min_df=2` (ignore words seen only once), `sublinear_tf=True` (dampens very repeated words).
**Important:** the vectorizer is fit on the training set only, then applied to the test set — otherwise test information leaks into training.

### Step 6 — Models (`train_baselines.py`)
Each model is trained separately for emotion and for sentiment:
- **Majority-class baseline** — always predicts the most common class; the "floor" to beat.
- **Logistic Regression** — linear model giving class probabilities.
- **Linear SVM** — finds the maximum-margin separating hyperplane; usually strongest on sparse TF-IDF text.
- **Multinomial Naive Bayes** — probabilistic model assuming word independence; fast but weaker.

### Step 7 — Evaluation
Metrics: **accuracy**, **macro-F1** (average F1 over classes, treats classes equally), per-class precision/recall, and a **normalised confusion matrix**.

### Step 8 — Streamlit app (`src/app.py`)

> **Update, 9 Nov 2026:** this step describes the original SVM app. The app now gets emotion and sarcasm from the transformer. See section 7A.
A small web interface so a user can try the model:
1. Loads the saved TF-IDF vectorizer and the two Linear SVM models from `models/` (cached with `st.cache_resource` so they load once).
2. The user types a social-media text (or clicks an example button) and presses **Analyze**.
3. All the prediction logic is in `predictor.py`. Recognised emojis are taken out of the text; the remaining words go through the **same `clean_text`** used in training, then `vectorizer.transform`.
4. Each SVM scores the words, the emojis add their vote (see *Emoji handling* below), and the app shows the emotion and sentiment with icons, bar charts, and a "How was this decided?" panel (emojis recognised, words-only prediction, confidence).
5. SVMs don't output probabilities, so the decision scores are passed through a **softmax** to show *relative* confidence. Say this is not a calibrated probability.
6. Guards: empty input warning; a message if no word was seen in training; a clear error if the model files are missing or were saved with a different scikit-learn version (fix: rerun `preprocessing.py` and `train_baselines.py`).

**Emoji handling (found during testing, then fixed and tested):**

*The problem.* "i guess i am happy 😄" was predicted as *sadness*. Two causes: (1) the training data has **no emojis at all**, because we deliberately removed the label-coded emoji suffixes, so the model cannot read emojis; (2) "happy" appears about equally in sadness (396) and joy (398) rows in this dataset, so the words alone are ambiguous.

*First attempt (rejected).* Replace each emoji with 3 emotion words (😄 -> "joyful glad delighted"). The emoji then always overpowered the text: "i feel so lonely and miserable 😄" -> joy. With text and emoji in conflict, the text's emotion won only **27%** of the time.

*Final solution: late fusion (`predictor.py`).*
1. Recognised emojis (about 100, in 6 groups, table `EMOJI_EMOTION`) are removed from the text and counted.
2. The words alone get SVM scores -> softmax -> `p_text`.
3. The emojis give their own vote `p_emoji` (e.g. one 😄 = 100% joy; for sentiment joy/love -> positive, anger/fear/sadness -> negative, surprise -> neutral).
4. **Final = (1 - w) x p_text + w x p_emoji**, with w = 0.25 for emotion and 0.30 for sentiment (sentiment SVM is more confident on its own, so it needs a larger emoji share). If no known words remain (emoji only), the emoji decides alone.
5. Effect: when the words show no clear emotion (the emotion model's top score on neutral sentences is ~0.2-0.27, close to 1/6 = random) the emoji decides; when the words are strongly emotional (top score 0.5-0.9) the text wins.
6. Ambiguous emojis (🥲 🙃 😅 🤔 😐 💀) are deliberately not mapped, so they are ignored.

*How w was chosen.* Tried w = 0.2 ... 0.5 on one set of sentences, then tested on a **different** set of sentences (to avoid tuning and testing on the same data).

*Robustness test results* (`test_emoji_robustness.py`; 10 neutral sentences x 18 emojis, plus emotional sentences; "expected" = human judgement):

| Test | Emotion correct | Sentiment correct |
|---|---|---|
| Same sentence + 1 emoji at the end | 100% (180/180) | 96.7% |
| Same sentence + 1 emoji at the start | 100% (180/180) | 96.7% |
| Repeated emoji (😭😭😭) | 100% | 96.7% |
| Emoji only | 100% (18/18) | 100% |
| Text and emoji agree | 100% | 100% |
| Text and emoji **conflict** -> text should win | **90%** (old approach: 27%) | **86.7%** (old: 57%) |
| Unmapped emoji (🥲 🤔 ...) | ignored, prediction unchanged in 100% of cases | |

*Remaining errors and why:* (a) "the bus was late again 😁" -> sentiment neutral, because the words are confidently neutral; (b) "i feel heartbroken and alone" -> sentiment *positive* even without an emoji, because the heuristic sentiment labels treat "heartbroken" as positive (a data/label problem, not an emoji problem); (c) when the text is only mildly emotional ("delighted and grateful" + 😭) the emoji can still win; (d) emotion and sentiment are predicted separately, so occasionally they disagree (e.g. fear + positive).

*Also important:* without an emoji, a neutral sentence ("dinner is ready") still gets one of the 6 emotions because the dataset has **no "neutral/no emotion" class**. The app shows a "weak guess" note when the words' emotion confidence is below 30%.

Observed behaviour: strong on clear emotion words ("terrified" -> fear, "furious" -> anger), weaker on subtle or context-dependent sentences, because TF-IDF ignores word order beyond bigrams and context.

## 5. Why the scores are so high (be ready for this!)
We inspected the highest-weighted features of the SVM:
- **Emotion:** top words are the emotion words themselves — anger: *dangerous, wronged, violent*; fear: *afraid, terrified*; love: *tender, caring, loving*; surprise: *amazed, shocked*. The dataset labels were derived from the emotion word in the sentence, so a bag-of-words model can read them off. Remaining errors are mostly **label noise** (e.g. "sad empty feeling again" labeled joy).
- **Sentiment:** top words for positive are *love, good, great*; negative: *hate, sad, pain*. For *neutral* the top words are *impressed, curious, amazed*, i.e. words not in a sentiment word list. The model has therefore **learned the labelling lexicon**, not real sentiment understanding.
- No test text also appears in the training set (checked), so this is not duplicate leakage.

## 6. Likely viva questions and short answers

**Q: What is the problem and the dataset?** Multi-class text classification of emotion (6) and sentiment (3) on ~417k short texts; after cleaning/balancing 58,980 are used.

**Q: What is data leakage and where did it occur?** Information about the label being present in the input. Emojis appended to texts encoded the labels; we removed them (44,650 rows) so the model must use language.

**Q: Why balance the data and how?** To make accuracy/F1 meaningful and avoid bias to big classes; done by undersampling with max-flow so emotion and sentiment are both exactly balanced.

**Q: Downsides of undersampling?** Discards data (416k -> 59k) and distorts the natural joint distribution.

**Q: Why TF-IDF and not raw counts?** It down-weights common words and highlights discriminative ones. Bigrams capture short phrases like negation.

**Q: Why fit the vectorizer only on train?** To avoid test information leaking into training and giving optimistic results.

**Q: Why stratified split?** Keeps class proportions the same in train and test.

**Q: Why macro-F1 as well as accuracy?** Macro-F1 averages per-class F1 so every class counts equally and exposes weak classes.

**Q: Why does Linear SVM beat Naive Bayes?** NB assumes words are independent; SVM learns discriminative weights over many correlated sparse features and handles high dimensions well.

**Q: Are 96% results trustworthy?** They are genuine on this data but reflect keyword-based labels. Sentiment labels are heuristic, so they do not prove real-world sentiment ability. Real-world accuracy would be lower.

**Q: How does the app work?** It cleans the input exactly as in training, converts it with the saved TF-IDF vectorizer, and runs the saved emotion and sentiment SVMs; scores are softmax-normalised to show relative confidence. Built with Streamlit, run by `streamlit run src/app.py`.

**Q: Why did the app get an emoji wrong, and how did you fix it?** The model never saw emojis (removed to stop leakage), and "happy" is ambiguous in this dataset. We use **late fusion**: the SVM scores the words, an emoji table gives a separate vote, and they are combined with a weight (25% emotion, 30% sentiment). The emoji decides when the words are neutral; strongly emotional words overrule it.

**Q: How did you test it?** Same sentences with 18 different emojis, at start/end, repeated, emoji-only, and text-emoji conflicts, on sentences not used to choose the weights. Emoji-following was 100% for emotion; in conflicts the text wins 90% (vs 27% with the first approach).

**Q: Is the emoji part machine learning?** No, it is a rule table combined with ML scores (a hybrid). A learned approach needs training data with real emojis, or a pretrained model such as an emoji-aware transformer.

**Q: Why are the model files saved?** So the app doesn't retrain; the vectorizer must be saved too, because new text must use the same vocabulary as training.

**Q: Limitations?** Emoji handling is a hand-made table (ambiguous emojis ignored, sarcasm not handled); no neutral emotion class; heuristic sentiment labels, label noise, bag-of-words ignores context and sarcasm, undersampling loses data, English only, a single split (no cross-validation).

**Q: Future work?** Hand-review the 500 ambiguous labels; improve emoji handling; train a Twitter-based sentiment model; cross-validation; deploy the app online.

## 7. Phase 2: Emoji-aware models and ambiguous text (experiments)

**Research question:** *To what extent can emoji-aware feature extraction improve sentiment and emotion classification on ambiguous social media text compared with conventional text-only machine learning approaches and rule-based emoji integration?*

### 7.1 Why this phase
The 0.96 / 0.95 scores come from a test split that looks exactly like the training data: 96.7% of texts start with "i"/"im", **zero emojis, zero non-ASCII characters**, and almost no slang. Real social-media text has sarcasm, slang and emojis, so we built a separate test set to find out how the system behaves there.

### 7.2 New architecture
```
text ──► predictor.py (existing, unchanged) ─────────────► A: words-only SVM
     │                                       └─ emoji table vote ─► D: A + emoji voting
     ├─► emoji_features.demojize ─► TF-IDF ─► SVM ─────────► B / B′
     └─► [text TF-IDF | emoji-name TF-IDF | emoji counts] (scipy hstack) ─► SVM ─► C / C′
```
All SVMs use the baseline settings (C = 0.5, TF-IDF 1-2 grams, 50k features, min_df 2) and the **same 80% training split**. Original models and `final.csv` are untouched; new models live in `models/experimental/`.

### 7.3 The ambiguous test set (dataset construction)
- 500 short sentences in 10 categories: sarcasm, irony, positive words with negative meaning, negative words with positive meaning, emoji-dependent sentiment, context-dependent emotion, mixed emotions, internet slang, contradictory text + emoji, neutral/ambiguous.
- **Paired groups:** 25 groups with identical text and a different emoji (e.g. "I'm fine" / 😊 / 🙂 / 🙂🔪 / 😭 / 😤), and 8 groups with the same emoji and different text (e.g. 😭 for grief, cuteness, laughter).
- 158 rows contain emojis; 0 overlap with the training data; it is **never** used for training or tuning.
- **Labels:** written as *suggestions* by an AI assistant (Claude), every row `pending_review`. The model and the emoji table were **not** used to label. 64 rows have no emotion label because none of the 6 classes fits (we flag rather than force). Mixed feelings have a `secondary_emotion`, and metrics report a strict and a lenient score.
- **Known bias risk:** the same assistant wrote D's emoji table and the augmentation pools, so D and B′ may be favoured until humans review the labels (`data/ambiguous_annotation_guide.md`).

### 7.4 Emoji processing techniques
- **Demojization with the standard library** (`unicodedata`) instead of the `emoji` package: same output on every machine, no new dependency, never skipped. Outdated Unicode names are replaced by modern CLDR names (❤️ "red heart", 😡 "enraged face", 🔪 "kitchen knife"). Skin tones and multi-part emojis stay together.
- **Repeat normalisation:** 😂😂😂 → 😂 (the repetition is kept as a numeric feature in C).
- **Model C numeric features:** log emoji count, emojis per token, has-repeat, longest repeat, distinct emojis.
- **Synthetic augmentation (B′, C′):** the training data has no emojis, so we made a copy where 50% of training rows get 1–3 emojis: 60% match the row's emotion, 25% are ambiguous (🙂 🤔 💀 …), 15% contradict it. Labels are never changed; seed 42. This **injects an assumed emoji prior**, so it tests whether a model can *learn* that prior alongside text, not real emoji usage.
- **Confidence:** B/C use sigmoid calibration (`CalibratedClassifierCV`, 3-fold, training data only) → calibrated probabilities; A/D show a softmax of SVM scores, which is **not** a probability.
- **Explanations:** C is linear, so each class score splits exactly into a text part and an emoji part; for B we measure the emoji effect by removing the emojis and comparing scores (ablation).

### 7.5 Results (AI-suggested labels — see `results/emoji_comparison/comparison_report.md`)
**Original test split:** every model scores the same as A (sentiment macro-F1 0.945–0.946, emotion 0.960–0.963). Emoji handling costs nothing on normal text.

**Ambiguous set, accuracy:**

| System | All sentiment | All emotion | Emoji rows sentiment | Emoji rows emotion | Sarcasm + irony sentiment |
|---|---|---|---|---|---|
| A text-only | 0.29 | 0.28 | 0.24 | 0.25 | 0.17 |
| B demojized | 0.34 | 0.31 | 0.39 | 0.35 | 0.17 |
| C hybrid | 0.29 | 0.28 | 0.24 | 0.25 | 0.17 |
| B′ demojized + aug | 0.32 | 0.40 | 0.32 | 0.60 | 0.17 |
| C′ hybrid + aug | 0.30 | 0.37 | 0.24 | 0.52 | 0.17 |
| D emoji voting | **0.39** | **0.40** | **0.56** | **0.63** | 0.17 |

(Random guessing: 0.33 sentiment, 0.17 emotion.) B, B′, C′ (emotion) and D are significantly better than A (exact McNemar, p < 0.05); on emoji-row emotion D vs B′ is **not** significant (p = 0.33); on sentiment D is significantly better than all.

**Paired emoji test:** A and C never react to an emoji (sensitivity 0). D reacts most (0.67 sentiment / 0.75 emotion) but is the least stable (0.46 / 0.52) and one emoji forces the same sentiment on 62% of same-emoji groups (😭 always means sadness, even for happy tears). No system is both sensitive and stable.

### 7.6 Main conclusions
1. **The existing model does not transfer to social-media text**: 0.95 → 0.29 sentiment. It predicts "neutral" for 58% of sentences because the training sentiment labels came from a word list.
2. **Separate emoji features (C) are useless without emoji training data.** C equals A exactly, because the emoji columns are always zero in training.
3. **Demojization (B) helps a little with no emoji data at all**, because emoji names reuse words the model knows ("crying", "fearful", "joy").
4. **Learning emojis from synthetic data (B′) gets close to the hand-made rules (D) for emotion**, but not for sentiment.
5. **Nothing fixes sarcasm, irony or context** (all systems 0.17 on sarcasm/irony sentiment). These need models that understand context, not better emoji handling.
6. Answer to the research question: **emoji-aware features improve emoji-dependent text but not ambiguity in general; with no real emoji training data, the rule-based integration (D) is still the strongest, and it over-trusts emojis.**

### 7.7 Limitations
- Labels are AI-suggested until reviewed, and the same assistant wrote the rules and the pools (possible bias toward D/B′).
- Small classes (love and surprise: 26 rows each) give noisy per-class scores; overall CIs are about ±0.04–0.08.
- B′/C′ learn an injected prior, not real emoji usage.
- Very new emojis may get the generic name "emoji" on older Python versions.
- The paired set has 33 groups; enough to see a clear trade-off, not to rank close systems.

### 7.8 Future improvements
Human review (two annotators, agreement score); real emoji-labelled social-media training data; a "neutral/no emotion" class; transformer models (BERTweet, twitter-RoBERTa) for sarcasm and context; tuning the fusion weight on a separate validation set.

### 7.10 Viva questions for this phase
**Q: Why did accuracy fall from 0.95 to 0.29?** Different distribution: the training text is "i feel …" sentences with no emojis or slang, and sentiment labels came from a word list. On sarcasm the model reads words literally ("Fantastic! My laptop crashed" → positive).

**Q: Why build your own test set, and how do you know its labels are right?** No suitable labelled data with paired emojis was available. The labels are AI-suggested and marked pending; final claims rely on the human-verified subset, reviewed with a written guide.

**Q: Why was Model C identical to the baseline?** Its emoji features were zero for every training row, so the SVM learned zero weights for them. Features can't learn from data that doesn't contain them.

**Q: Then why did Model B help?** Demojization turns 😭 into "loudly crying face", and the model already knows "crying". It is transfer through shared vocabulary, not emoji learning.

**Q: Isn't synthetic augmentation cheating?** It would be if it touched the test set or the labels; it does neither. But it injects our own assumption about emojis, so B′ shows how well a model can learn that assumption, not real emoji meaning. We added 25% ambiguous and 15% contradicting emojis so the model can't learn "emoji = label".

**Q: How do you know the differences are real?** Bootstrap 95% confidence intervals and exact McNemar tests on the same rows. Some differences are significant (D vs A); some are not (D vs B′ on emotion).

**Q: What is calibration and why use it?** SVMs output distances, not probabilities. Sigmoid (Platt) calibration fits a mapping from scores to probabilities on held-out folds of the training data, so "80%" means roughly 80% correct.

**Q: What is the sensitivity–stability trade-off?** Sensitivity = the prediction changes when the emoji changes the meaning; stability = it stays when the emoji doesn't. A ignores emojis (stable, insensitive); D follows them (sensitive, unstable). No system does both.

**Q: Final answer to the research question?** Emoji-aware features help only on emoji-dependent text, and only if the model has emoji-aware training signal (real or synthetic); they do nothing for sarcasm, irony or context. Rule-based voting is still strongest on emoji rows but over-trusts emojis.

## 7A. Phase 3: Transformer, sarcasm and the current app

### Why this phase
The SVM scored 0.963 on its own test split but only 0.303 accuracy (0.284 macro-F1) on human-labelled GoEmotions text. Its top features were emotion keywords, because the training sentences are mostly "i feel X". A random split of one dataset cannot reveal that. Only a separately collected test set can.

### What the app uses now
| Part | Method |
|---|---|
| Emotion (7 classes) | `cardiffnlp/twitter-roberta-base-2022-154m`, fine-tuned on GoEmotions + SemEval-2018 Affect in Tweets + 462 sarcastic tweets labelled from their authors' rephrases |
| Sarcasm | A second output on the same model, trained on iSarcasmEval + SemEval-2018 irony, with GoEmotions comments as not-sarcastic examples |
| Emojis | Fusion with the rule table: weight 0.25, or 1.0 when there are no words |
| Sarcasm rule | If P(sarcastic) >= 0.90 and the top emotion is joy or love, take the best emotion other than joy, love or neutral |
| Sentiment | Existing TF-IDF + Linear SVM. It ignores sarcasm, and the app says so |

### Sarcasm and tweet data
Sarcasm: 10,214 rows. Tweet emotion: 5,521 rows. Author rephrases of sarcastic tweets are non-sarcastic training rows. Checks: no text shared between splits, none shared with the 500 ambiguous rows.

**Leakage found and removed:** in the raw irony test file every ironic tweet had a hashtag such as `#not`, and tweets without one were never ironic. The build script strips those hashtags.

**Licences:** iSarcasmEval's repo is MIT. TweetEval is listed as unknown and the SemEval-2018 Affect terms were not confirmed, so do not republish the tweets. The CSVs are gitignored.

### Results for the shipped setup
Ambiguous-set figures hide neutral, as in section 7, and use AI-suggested labels that are not human-reviewed. The previous best on the ambiguous set is system D, the SVM with emoji fusion.

| Measure | Previous best | App now |
|---|---|---|
| Natural test macro-F1 (7 classes) | 0.670 | 0.688 |
| Ambiguous set, overall | 40.1% | 42.4% |
| Ambiguous set, sarcasm rows (n=40) | 22.5% | 27.5% |
| Ambiguous set, all emoji rows | 63.0% | 50.0% |
| Positive words, negative meaning | 35.0% | 32.5% |

Sarcasm flag on held-out tweets: precision 70.5%, recall 33.5%, F1 0.454 on iSarcasm; precision 78.3%, recall 51.1%, F1 0.619 on SemEval irony. A TF-IDF baseline scored F1 0.339 and 0.540.

`results/sarcasm_emotion_v3/metrics.json` records the rule at the original 0.5 threshold, which is not the shipped setup. The shipped numbers above come from the 0.90 threshold.

### Mistake found while connecting the model
With the pre-declared threshold of 0.5, ambiguous accuracy looked strong (45.0%, sarcasm rows 50%). But running the whole pipeline on ordinary text showed natural-test macro-F1 falling from 0.687 to 0.569, and "I love my mom so much" became anger. The sarcasm output had only ever seen tweets, so it flagged about a quarter of ordinary comments. The fix was a threshold chosen on validation data: the lowest that costs at most 0.005 macro-F1. For that first model it was 0.998, with natural macro-F1 0.684, sarcasm rows 32.5%, and iSarcasm recall 23.5%.

### Retraining experiments
**Version 2 (not used):** also taught the sarcasm output that GoEmotions comments are not sarcastic. At its validation-chosen threshold of 0.98, natural macro-F1 rose to 0.695 and the ambiguous set to 43.6%, but sarcasm rows fell to 20.0% and iSarcasm recall to 19.5%.

**Version 3 (used by the app):** kept that change and added emotion labels for sarcastic training tweets. `label_sarcasm_emotions.py` scores each author's plain rephrase and gives its emotion to the sarcastic tweet, keeping non-neutral rephrases at 60% confidence or higher (462 tweets, each counted 3 times). These are machine-made labels, so some are wrong. Without any sarcasm rule, sarcasm rows rose from 0% in the first model to 25%, showing the emotion output itself learned from them. The chosen threshold is 0.90.

Version 3 met 3 of 5 pre-set targets against the first model. It missed sarcasm rows (27.5% against 32.5%, 2 rows of 40) and emoji rows (50.0% against 54.8%). It was chosen because sarcasm is the main goal and its sarcasm F1 was higher on both larger held-out sets. The cost is more false alarms: precision on iSarcasm fell from 85.5% to 70.5%.

### Viva questions for this phase
**Q: Why not just report 0.963?** It only shows the model can reproduce a dataset built around emotion keywords. It does not transfer to natural text.

**Q: How does the model handle sarcasm?** One output detects it, and a fixed rule removes joy and love when the model is very sure. The emotion output also learned from sarcastic tweets labelled through their authors' rephrases, so it reads some sarcasm without the rule.

**Q: What is the biggest remaining weakness?** It misses about two-thirds of sarcasm on iSarcasm, about 3 in 10 flags there are wrong, and emoji rows score below the older SVM setup. Sentiment is also weak (0.510 accuracy on TweetEval).

**Q: Are the ambiguous results final?** No. All 500 labels are AI-suggested until reviewed by a human, and some subsets are small (40 sarcasm rows, so one row is 2.5 points).

## 8. Glossary
- **Macro-F1:** mean of per-class F1 scores. **F1:** harmonic mean of precision and recall.
- **Precision:** of predicted X, how many were X. **Recall:** of actual X, how many were found.
- **n-gram:** sequence of n consecutive words. **Stratified:** preserving class proportions.
- **Undersampling:** removing rows from larger classes. **Target leakage:** label information hidden in the input.
- **Calibration:** turning model scores into probabilities that match observed accuracy.
- **McNemar test:** compares two classifiers on the same examples using only the cases where they disagree.
- **Bootstrap confidence interval:** resample the test rows many times to see how much a score could vary.
- **Demojization:** replacing an emoji with its name in words.
- **Data augmentation:** creating modified copies of training examples (here: adding emojis) without changing labels.
- **Distribution shift:** the test data differs in style or content from the training data.
